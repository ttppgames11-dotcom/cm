# 1-to-1 Meetings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Real, private, live 1-to-1 business meetings: request, accept or decline, cancel, complete, reschedule, shared note, between members who own a business.

**Architecture:** A new `MeetingService` and `MeetingController` in the existing `sangam` feature (mirroring `ReferralService`), using the existing `meetings` table through `MeetingRepository`. Changes publish `MeetingChanged` after commit and a relay pushes ids and status to an SSE channel. The website page is rewritten around a pure helper module and an EventSource hook, reading only server data.

**Tech Stack:** Java 17, Spring Boot 3.3.5, JPA/native SQL and JdbcTemplate, PostgreSQL (embedded for tests), MockMvc, SSE; React 18 + Vite, `node --test`.

**Spec:** `docs/superpowers/specs/2026-10-27-meetings-design.md`

## Global Constraints

- Backend on `Abhay_app` in `E:\community_mobile`; website on a branch off `main` in `E:\community_mobile_main`. Pushes as abhayGond02. Never upload `database/connect_maratha.db`.
- Routes (all under `/api/sangam/meetings`): `GET ""` and `GET /partners` and `POST ""` and `PUT /{id}` and `PUT /{id}/status` and `PUT /{id}/notes` are `@RequireAuth` (401 without a login); `GET /stream` is open like the referral stream (see Ruling R1).
- Statuses stored: `Requested`, `Confirmed`, `Declined`, `Cancelled`, `Completed`. Create inserts `Requested`. Status body words: `accepted`, `declined`, `cancelled`, `completed` (lower case, trimmed; anything else is a 400 `VALIDATION_ERROR`).
- Transition rules: `accepted` and `declined` only by the recipient and only from `Requested`; `cancelled` by requester or recipient from `Requested` or `Confirmed`; `completed` by requester or recipient only from `Confirmed` and only when the meeting date is today or earlier (Asia/Kolkata). Reschedule (`PUT /{id}`) by either participant from `Requested` or `Confirmed`, validated like create, status becomes `Requested`. Notes by either participant, up to 2000 characters. Admins can read every meeting but change none. A non-participant gets 403 `FORBIDDEN`, an unknown id 404 `MEETING_NOT_FOUND`, a wrong-state change 400 `INVALID_TRANSITION`.
- Create body: `recipientId` (required, max 20), `date` (`YYYY-MM-DD`, a real calendar date, today or later in Asia/Kolkata), `time` (`HH:mm`, 24 hour; if the date is today it must be later than now), `mode` (`Offline` or `Online`), `place` (required, max 200; for `Online` it must start with `http://` or `https://`), `topic` (required, 3 to 300 characters). snake_case `recipient_id` is accepted as an alias.
- Create rules: the recipient is not the caller and owns a visible business (`ReferralReceiverRepository.ownsVisibleBusiness(String)`), else 400 `RECIPIENT_NOT_ELIGIBLE`; no other open meeting (`Requested` or `Confirmed`) between the same two members in either direction (400 `DUPLICATE_REQUEST`); a member has at most 10 requests in `Requested` (400 `TOO_MANY_OPEN_REQUESTS`); `MeetingLimiter` allows 20 creations per member per 24 hours (429 `RATE_LIMIT_EXCEEDED`). Requester id and name come from the login and the `members` row only; no body field can set them and nothing is invented.
- `GET ""`: each caller sees only meetings where they are requester or recipient, newest date first; an admin sees all, and only an admin may narrow with `memberId`. Each row has the usual snake_case fields plus `mode`, `role` (`requester`, `recipient`, or absent for an admin who is neither) and `partner_id`, `partner_name` (the other person; absent for that admin).
- The `meetings.mode` column is added on first use with `ALTER TABLE meetings ADD COLUMN IF NOT EXISTS mode TEXT` (`LazyTables.ensureMeetingColumns()`, same pattern as `ensureReferralColumns`) and as migration `database/migrations/010_meetings_mode.sql`; it is read and written with `JdbcTemplate`, not mapped on the `Meeting` entity. Old rows without `mode` read as `Offline`.
- Live event: channel `meetings`, event name `meeting.changed`, payload exactly `{id, requesterId, recipientId, status}`: no topic, place, date, time, name or note.
- Notifications use `ActivityRepository.notifyMember(...)` (the other side is told on request, accept, decline, cancel, reschedule); audit lines use `ActivityRepository.audit(...)` for cancel and complete as before.
- Test member ids for this feature use `M98xx`; test businesses are named `Zm...`; tests clean their own rows in `@BeforeEach`.
- Existing 159 backend tests and the Node comparison stay green except the meetings requests, which move out of the comparison (Task 1). Website tests with `node --test <file>` (directories do not work) and `npm run build`.

## Rulings made while planning

- **R1:** The spec said the stream needs a login. Browsers cannot send a login header on `EventSource`, and the referral stream is open with ids and status only. The meetings stream does the same, carrying only the four fields above; every page reloads its own private list after an event. Cost if wrong: an outsider can see that two member ids had a meeting change (no content).
- **R2:** "Today" and "now" mean Asia/Kolkata, since all members are in India. Cost if wrong: a meeting booked near midnight in another zone is judged by Indian time.

## Review Focus

- **Impossible or past dates** (`2026-02-30`, yesterday, today with a time already gone, `25:99`): 400 with a message, nothing saved. Test in Task 1.
- **An online link that is not a web address** (`javascript:alert(1)`, plain text): refused, so the page never renders a dangerous link. Test in Task 1.
- **A second request to the same person, or more than 10 open requests:** refused clearly. Test in Task 1.
- **Wrong person or wrong moment** (the requester accepting their own request, accepting twice, accepting after a cancel, a stranger touching a meeting, completing before the day): 403 or 400, nothing changed. Tests in Task 2.
- **Privacy:** a stranger's list is empty of other people's meetings, and the live event holds no meeting content. Tests in Tasks 1 and 3.
