# CRM Staff (Step 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A unit's owner (or an admin) adds existing members as staff of the unit; staff see only their own unit and change nothing; the team is limited to 10.

**Architecture:** Builds on Step 1 (`crmunit` package, `CrmScope`, table `crm_unit_members`). Staff are rows with `unit_role = 'staff'`; no new table. `CrmScope` gets a `staff` kind; `CrmUnitService` gets `listStaff`, `addStaff`, `removeStaff`; the website adds a Staff section to the unit card.

**Tech Stack:** Java 17, Spring Boot 3.3.5, JdbcTemplate, PostgreSQL (embedded for tests), MockMvc; React 18 + Vite, `node --test`.

**Spec:** `docs/superpowers/specs/2026-11-02-crm-staff-design.md`

## Rulings made while planning

- **R1:** the owner-only unique index stays as it is; staff rows are many per unit. The 10-seat limit is enforced in the service inside the transaction after `SELECT id FROM community_centers WHERE id = ? FOR UPDATE` on the unit row, so two adds serialise. Cost if wrong: an 11th staff member in a very tight race.
- **R2:** staff `contains(path)` means the path is equal to the staff member's own unit path, never a prefix. `containsParentOf` stays false for staff (they cannot write). Cost if wrong: staff would see child units.
- **R3:** `GET /units/{id}/staff` also lets a staff member read their own unit's team (names only, no phones). Phones go only to the unit's owner and to admin / superadmin. Cost if wrong: a phone leak to staff.
- **R4:** an owner of a unit above can list a team but gets 403 on add / remove (spec decision); the CEO can list (names only) but gets 403 on add / remove.

## Review Focus

- **Staff scope is equality, not prefix:** staff of `/…/UNIT-DIS-1/` must not see a child taluka or the lookalike `UNIT-DIS-10`. Test in Task 1.
- **Removed staff lose access on the next request, and so do staff of an archived unit.** Tests in Task 1 and Task 2.
- **Seat race:** two simultaneous adds for the 10th seat → one 201, one 409 `STAFF_LIMIT`; the same member added to two units at once → one wins. Test in Task 2.
- **Nobody manages staff by accident:** staff, an owner of a unit above and the CEO all get 403 on add and remove. Test in Task 2.
- **Phone leak:** staff and owners above never see phone numbers in the team list. Test in Task 1 (list) and Task 2.

### Task 1: Backend — the staff kind in `CrmScope`, `/me`, list scope and the team list

- Consumes: Step 1 `CrmScope.Scope(kind, unitId, unitRole, path, write)`, `CrmUnitRepository`, `CrmUnitService.unitJson`.
- Produces:
  - `CrmScope.of`: a member with `unit_role = 'staff'` in an active ladder unit → `new Scope("staff", unitId, "staff", path, false)`.

**Interfaces:**
- Consumes: Task 1 and Step 1 (`CrmUnitSchemas.OWNER`, `normalize`, `resolveOwner` logic, `releaseFromArchived`, `inAUnit`, `send`, `audit`, `tx`).
- Produces:
  - `CrmUnitRepository`: `lockUnit(String id)` (`SELECT id FROM community_centers WHERE id = ? FOR UPDATE`), `linkStaff(memberId, unitId) -> int` (`INSERT … 'staff' ON CONFLICT DO NOTHING`), `unlinkStaff(memberId, unitId) -> int` (`DELETE … AND unit_role = 'staff'`).
