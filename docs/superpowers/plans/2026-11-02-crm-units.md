# CRM Units (Step 1) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Admins create a ladder of units (State → Branch → Division → District → Taluka), each with one owner who is an existing member; an owner sees and manages only their unit and everything below it; the rules for who sees what live in one class and are checked on every request.

**Architecture:** A new `crmunit` feature (Controller → Service → Repository, JdbcTemplate) at `/api/crm-hierarchy`. It extends the existing `community_centers` table with ladder columns and adds `unit_id` / `unit_role` to `members` (migration 017 + `LazyTables`). A single `CrmScope` class reads the member row from the database and decides scope; no endpoint decides on its own. The website ports the other developer's `UnitHierarchyPanel` onto a new page `/crm/units`.

**Tech Stack:** Java 17, Spring Boot 3.3.5, JdbcTemplate, PostgreSQL (embedded for tests), MockMvc; React 18 + Vite, `node --test`.

**Spec:** `docs/superpowers/specs/2026-11-02-crm-units-design.md`

## Rulings made while planning

- **R1:** `community_centers` has no migration (it is created lazily with `created_at TEXT`). Migration 017 therefore starts with `CREATE TABLE IF NOT EXISTS community_centers` (same columns as `LazyTables.COMMUNITY_CENTERS`) and then `ALTER TABLE … ADD COLUMN IF NOT EXISTS`. `LazyTables.ensureWebsiteTables()` also runs the ladder `ALTER`s so old code and new code see the same table. Cost if wrong: none (idempotent).
- **R2:** Ladder units must not appear in the old front-desk lists: `CommunityCenterRepository.findActive` and `find` get `AND c.level IS NULL`. Cost if wrong: ladder units would show as front-desk centres.
- **R3 (changed in execution, R6):** see R6.
- **R4:** `path` includes the unit itself (`/UNIT-STA-1/UNIT-BRA-7/`); "inside my scope" means `path LIKE ownerUnitPath || '%'`. "Above the unit" means the actor's scope contains the unit's **parent** path (or the actor is a global writer), so an owner cannot change their own unit's owner or archive it.
- **R5:** `GET /units` for an actor with no access returns `{units: []}` with 200 (the page shows "no access" from `/me`); writes return 403 `NO_ACCESS`.
- **R6 (ruling during Task 1):** the member-to-unit link is a new table `crm_unit_members (member_id PK, unit_id, unit_role, created_at)` with a unique index "one owner per unit", NOT columns on `members`. Reason: Node returns every `members` column, so new columns changed its `/me` JSON and failed `NodeParityTest`. Everywhere this plan says `members.unit_id` / `unit_role`, read `crm_unit_members`. Cost if wrong: one extra join.

## Review Focus

- **Stale token:** a member whose token still says `admin` or owner but whose database row says otherwise gets no access (scope is read from the row). Test in Task 1.
- **Sibling leak:** an owner asking for a sibling unit or its children gets 404, and `search` / `parentId` / `level` filters never widen the scope. Test in Task 1.
- **Prefix trap:** a unit whose path merely starts with the same characters (`/UNIT-DIS-1/` vs `/UNIT-DIS-10/`) must not be in scope. Test in Task 1 (paths end with `/`).
- **Concurrent creates:** two simultaneous creates of the same name under the same parent → one 201, one 409 `UNIT_EXISTS`; two creates giving the same member as owner → one wins (409 `OWNER_IN_UNIT`). Test in Task 2.
- **Archived or replaced owners:** archiving a unit, or replacing its owner, removes access on the next request; archived units reject edits and new children. Test in Task 2.

### Task 2: Backend — create, edit, archive, change owner

**Interfaces:**
- Consumes: Task 1 (`CrmScope`, `Scope`, `CrmUnitRepository`, unit JSON).
- Produces:
  - `CrmUnitSchemas.CREATE` (`level` required, `oneOf` the levels; `name` required, 2–100; `parent_id` ≤ 60; `address` ≤ 300; `state`, `division`, `district`, `taluka` ≤ 100; `owner` an object with `member` ≤ 30 or `phone` of 10 digits, at least one), `UPDATE` (`name`, `address`, `status` `oneOf active, archived`), `OWNER` (`member` or `phone`); `normalize` maps camelCase (`parentId`) the way `OfficerSchemas.normalize` does.
  - `CrmUnitRepository`: `insert(Map) -> int`, `update(id, Map) -> int`, `setStatus(id, status) -> int`, `setOwner(unitId, ownerId) -> int`, `linkMember(memberId, unitId) -> int` (conditional `UPDATE members SET unit_id = ?, unit_role = 'owner' WHERE id = ? AND unit_id IS NULL`; 0 rows → `OWNER_IN_UNIT`), `unlinkMember(memberId)`, `membersByIdOrPhone(String) -> List<Map>`.
  - Routes `POST /units` (201), `PUT /units/{id}`, `POST /units/{id}/owner`.
  - Audit actions `CRM_UNIT_CREATE`, `CRM_UNIT_UPDATE`, `CRM_UNIT_ARCHIVE`, `CRM_UNIT_RESTORE`, `CRM_UNIT_OWNER_CHANGE`. Notifications of type `crm_unit`: new owner title `🏢 तुम्ही युनिटचे मालक आहात`, message `{unit name} युनिटचे मालक म्हणून तुमची नेमणूक झाली`; old owner title `{unit name} युनिटची मालकी काढली`.

- [ ] **Step 1: Write the failing tests** in `CrmUnitWriteTest`:
  - `adminCreatesAStateWithAnOwner` (201; the row has `path /UNIT-STA-…/` and `owner_id`; the owner's `members.unit_id` and `unit_role owner`; the owner gets one `crm_unit` bell; audit row `CRM_UNIT_CREATE`; the owner's `/me` shows the unit).
  - `onlyAdminsCreateAState` (owner of a branch posting `level state` → 403 `NO_ACCESS`; CEO → 403; visitor → 401).
  - `levelMustSitDirectlyBelowTheParent` (district under a state → 400 `INVALID_LEVEL_ORDER`; state with a `parent_id` → 400; unknown parent → 404 `UNIT_NOT_FOUND`; branch under an archived state → 409 `UNIT_ARCHIVED`).
  - `ownerCreatesBelowOnly` (a branch owner creates a division under their branch → 201 with a path that extends the parent's; under a sibling branch → 404; a branch next to their own → 400 `INVALID_LEVEL_ORDER`).
  - `ownerMustBeAFreeNonAdminMember` (unknown member → 404 `MEMBER_NOT_FOUND`; a member who already owns a unit → 409 `OWNER_IN_UNIT`; admin or CEO as owner → 400 `OWNER_NOT_ALLOWED`; a phone shared by two members → 409 `MEMBER_AMBIGUOUS`; a phone with spaces or dashes works).
  - `sameNameUnderTheSameParentIsRefused` (case-insensitive: `Zq Satara` vs `zq satara` → 409 `UNIT_EXISTS`; the same name under another parent is fine; the failed create leaves no member link and no bell).
  - `badBodiesAreRefused` (missing name / level / owner, name of 1 character, level `village`, owner `{}` → 400 naming the field).
  - `editChangesNameAndAddressOnly` (an owner edits their own unit → 200 and `CRM_UNIT_UPDATE` audit; a body with `level`, `parent_id`, `path`, `owner_id` changes nothing; a sibling's unit → 404; CEO → 403; renaming to a taken sibling name → 409).
  - `archiveAndRestoreNeedSomeoneAbove` (the owner of a branch archives a district below → 200 and that district owner's `/me` is `none` at once; restore → access back; the district owner archiving their own unit → 403; an archived unit rejects edits and new children with 409 `UNIT_ARCHIVED`).
  - `changeOwnerMovesAccessAtOnce` (admin changes a branch's owner: the old owner's `members.unit_id` is NULL and their `/units` is empty on the very next request, the new owner sees the unit; both get a bell; audit `CRM_UNIT_OWNER_CHANGE` with both ids; the unit's own owner changing the owner → 403; the same member again → 200 without a bell; a new owner who is already in a unit → 409 and the old owner keeps access).
  - `twoSimultaneousCreatesOneWins` (two threads POST the same name under the same parent → exactly one 201 and one 409; two threads creating different units with the same owner member → one 201, one 409 `OWNER_IN_UNIT`, exactly one unit row kept).
  - `aFailedBellDoesNotUndoACreate` (use the same technique `OfficerRequestsTest` uses for a failing notification: the create still returns 201 and the unit exists).
